# Backend–frontend completion coverage

Audit date: 2026-11-06 (Asia/Dhaka). Inspection only. No tests, builds, application launches, network probes, installations or source changes were performed. Only this report and [COMPLETION_ROADMAP.md](COMPLETION_ROADMAP.md) are audit deliverables.

## Executive assessment

Attorlink has substantial real REST implementation, not merely static screens: authentication, encrypted Android session persistence, client/lawyer profiles, professional records, discovery/community, REST messaging, in-app notifications, call lifecycle/scheduling, boost purchase lifecycle, security and support are represented in reachable workflows. Request envelopes, ownership guards, session generations and error handling were inspected against backend implementations, not just endpoint names.

It is **not yet a fully functional Android application proven against the backend**. Audio/video transport is absent; checkout is a backend sandbox demonstration, not production payment processing. Sponsored-visit linkage and safe generic asset deletion cannot be completed from the exposed contracts. Additional notification/qualification lifecycle defects are documented below. Android native bridges have historical compilation evidence, but no genuine device execution evidence. Authenticated live integrations remain unverified.

### Counting and classification

The operation matrix contains **242 operations: 239 REST handlers, one STOMP SEND handler and two outbound event destinations**. Thirteen REST handlers are alternative multipart save encodings, counted separately because they are distinct handlers. Nine ADMIN-only reference writes and admin-package controllers are excluded. Framework health/docs/SockJS handshake paths, internal jobs, DTO variants and nonexistent APIs are not additional domain operations.

These flags apply to the broader behavior described in each note, not necessarily to the ability to execute the HTTP request. All **242 are U — runtime UNVERIFIED**. MySQL/API availability, SMTP, Cloudinary and other provider requirements are listed separately as conditional runtime prerequisites: this audit did not probe them or count unknown availability as a confirmed outage. Counts are traceable to matrix rows and are not a completion percentage.

## Evidence conventions and shared implementation

Backend paths in the matrix are relative to `../attorlink-backend/src/main/java/com/attorlink/`; links identify the actual handler and line. REST paths are shown in full. Each row's family joins to the implementation/authorization/test tables below, avoiding repeated long paths. Test names are relative to `test/`; family test evidence does not imply each operation has an individual test. All matrix rows inherit U.

`lib/core/network/api_client.dart`, `api_response.dart`, `api_exception.dart` and platform transports implement authenticated requests, backend envelopes, field errors, binary PDF responses and access/session guards. `lib/features/auth/domain/session_controller.dart` owns refresh/session generation. Guards suppress stale account responses and recheck access before requests; they cannot undo requests already accepted by the server. Network uncertainty must not be interpreted as a successful mutation or as proof that retry is safe.

`lib/app/attorlink_app.dart`, `app_services.dart`, `app_shell.dart` and `features/auth/presentation/auth_gate.dart` wire the real workspaces. Discover, Community and Messages retain visited tabs; Account selects client/lawyer workspace; app-bar actions expose notifications/calls/settings; support is inside Settings and boosts inside the lawyer workspace. Home remains a placeholder, but there is no corresponding home-dashboard backend contract to invent. Discovery-to-message prefill is absent; manual recipient-ID start is reachable, so this is navigation friction rather than a missing conversation endpoint.

## Contract findings by workflow

### Authentication, role selection and security

Inspected `auth/controller`, `auth/dto`, `auth/service/AuthServiceImpl`, `PasswordServiceImpl`, `RefreshTokenService`, account/2FA/session services; `user/controller/UserController`, user settings services and DTOs; JWT/HTTP/WebSocket security configuration. Signup uses actual email/password/confirmation fields and optional phone; signup verification/resend returns messages rather than a successful logged-in session. Login handles either token/user success or a 2FA challenge. Challenge verification follows the backend challenge-token/OTP contract; an invalid attempt can consume the challenge. Forgot-password verification returns the reset credential for confirmation; authenticated reset uses current/new/confirmation and OTP. No unsupported recovery-code API was inferred.

Flutter access/refresh tokens are session-bound, refresh is single-flight, rotation clears superseded persisted credentials, and ambiguous refresh outcomes require login rather than replaying a stale refresh token. Android restoration revalidates through the backend. Local logout clears credentials even if remote logout fails, with failure feedback; that is not proof of server revocation. Role choice is CLIENT/LAWYER only, not an administrator entry point. Password/2FA 401s are not blindly replayed as access-token expiry; security operations recheck the session appropriately.

Privacy uses actual message/comment enums; notification preferences use social, messaging, lawyerActivity and system booleans. TOTP setup supports explicit secret/manual enrollment without persisting secrets. Session listing/revocation lacks a reliable current-device marker; Flutter rechecks instead of inventing one. Deletion requests/OTP schedule deletion; login restoration is backend behavior, not a frontend undelete endpoint. History is unpaged; no separate deletion-status or recovery-code API exists.

**Backend security risks requiring runtime evidence/owner review:** `RefreshTokenService.validate` invokes revocation and then throws inside a transaction; rollback may undo intended reuse revocation. Mock verification of a revoke call does not prove committed DB state. `AuthServiceImpl.login` restores scheduled-deletion accounts before optional 2FA; refresh/challenge completion and JWT status handling need suspension/deletion tests. These are not claimed as reproduced vulnerabilities and are not Flutter-only fixes. Already-issued JWT validity is not necessarily immediately ended by refresh-session revocation.

### Profiles, references and professional records

Inspected client/lawyer controller DTOs and corresponding services, qualification/practice repositories, upload validation and ownership lookups. CLIENT profile/address/preferences use real replacement/nullable semantics, active reference IDs and decimal coordinates. Lawyer profile updates preserve optional merge behavior; uploads return `url`/`publicId`. Verification submission requires first name, bar registration number and a saved Bar Council record; it does not justify inventing a universal mandatory-document requirement. Submitted/in-review/verified resubmission restrictions remain server-authoritative.

Council, High Court and Supreme Court are singleton records with supported dedicated document routes. Awards, bar associations, credentials, education, experience, memberships, publications and training have own-list CRUD; there is no per-ID GET or pagination to fabricate. Record details resolve from the own list. Saving reviewed qualification information may reset its review state to PENDING independently of overall lawyer verification. Existing attachments are preserved through GET-before-save; F3 concerns its lifecycle, not a request-field mismatch. Bar association/publication attachment links use generic DOCUMENT upload and JSON save; unlinking is not proof of provider deletion.

Specializations, jurisdictions, courts, languages, offices and services use actual list/create/update/delete contracts and relationship IDs. Reference reads expose active records; writes are ADMIN-only. Services use backend delivery type/fee/currency fields, not consultation booking. Weekly availability uses DayOfWeek and LocalTime; complete replacement omits unavailable days, because the save service normalizes persisted slots to available. No timezone or per-slot appointment API exists.

### Discovery and community

Inspected discovery specifications/service/response DTO, Post/Comment/Follow/Report/FeedAnalytics controllers and implementations, vote/bookmark/media ownership and feed queries. Discovery accepts search/practiceAreaId/page/size (size capped at 50), with server-defined updatedAt/id ordering. Only active verified lawyers appear. Summary fields are profile/user IDs, available name/photo/title/bio/experience/practice-area/update data; full other-lawyer qualifications, services, ratings and availability are not exposed. Flutter renders only returned summary information.

Feed categories are FOR_YOU, FOLLOWING, LATEST and TRENDING; FOLLOWING is client-only. Redis caching can fall back to database reads. Text/image posts use actual text/media-publicId fields; unsupported video/poll/question creation is not offered. Media must be owned and valid. Post editing can replace an image but does not expose a supported remove-image/type-change operation. Author IDs are not fabricated display names. The DTO does not provide every possible engagement count or bookmark state. Share records a backend event; it is not an invented share-link API. Own-post management filters visible general pages; server totals are not “my posts” totals.

Likes and comment votes use backend toggle/removal semantics; bookmarks have separate save/remove/list routes. Comment/reply CRUD is ownership-restricted and honors comment privacy. The comments repository query returns all undeleted post comments, including replies (B6), rather than a root-only forest; Flutter shows parent IDs and supported reply lists. Reporting supports POST/COMMENT targets and actual reason enums, not users; duplicate/self-report rules remain server-authoritative. Analytics retains actual fields and date ranges; some counters are lifetime and some windowed, and summary access is not necessarily author-only. Unknown image-upload outcomes cannot be recovered through an asset lookup API.

### Messaging, synchronization and notifications

Inspected `ChatConversationController`, `ChatMessageController`, `ChatWebSocketController`, chat services/repositories/DTOs, STOMP inbound authorization, `NotificationController`, notification service/preferences/delivery and payload DTOs. Conversation creation uses recipient ID and optional first text (up to 4000); an existing conversation can be returned without applying the supplied initial text. Accepted conversation membership is required for ordinary send; request recipient decides accept/reject. There is no invented client–client chat or attachment support. Message edits/deletions and recipient receipts preserve stable IDs and tombstones. Read markers are not simulated receipts.

History is oldest-first paginated. Sync uses timestamp/id cursors with a bounded result limit; edits and receipt changes are not a complete cursor change stream (B5). Flutter merges content and receipts independently, rejects stale generations, retains tombstones and reconciles with REST history. Outgoing requests filter an already-paged conversation result and expose misleading filtered totals (B4); the Sent inbox alternative helps but cannot repair server paging. Conversation detail's default unread count and viewer-relative delivery states are not treated as definitive sender read evidence. No send idempotency key means exactly-once send after timeout cannot be guaranteed.

SockJS handshake uses the configured endpoint (default `/ws`), `/info`, and a server/session WebSocket path. `stomp_codec.dart` handles actual framing; JWT is in STOMP CONNECT Authorization, never a URL token. Private chat subscription requires accepted membership; notification delivery is private per user. Only `/app/chat.send` has a SEND handler; an authorized-looking `/app/chat/conversation/*/send` pattern is not an implementation. Flutter deliberately sends over REST. The STOMP handler broadcasts its sends; ordinary REST edits/deletes/receipts do not all emit equivalent chat events. Foreground REST ticks and reconnect reconciliation remain required. WebSocket-only SockJS is accurately described; no XHR fallback, mobile push or background delivery guarantee is claimed.

Notification reads/count/read-all use own-user REST and actual event DTOs. Count/read-all reconciliation handles concurrent arrivals without locally marking unseen arrivals read. Message IDs do not imply conversation IDs; comment IDs do not imply post IDs; VIDEO_CALL IDs can refer to different namespaces, so fallback inbox navigation is appropriate. USER targets require the F1 correction below.

### Calls, scheduling and media

Inspected `VideoCallController`, `ScheduledVideoCallController`, their request/response DTOs, both service implementations and `LiveKitVideoMediaService`. Immediate states are INITIATED, RINGING, ACCEPTED, REJECTED, CANCELLED, ENDED, MISSED and FAILED. Scheduled states are SCHEDULED, RESCHEDULED, READY, STARTED, CANCELLED, MISSED and FAILED. Caller/callee/participant permissions and legal transitions are backend-authoritative. Provided conversation IDs must contain both users and be accepted; do not impose unrelated chat type restrictions on a call without a conversation.

Scheduling uses LocalDateTime without a timezone contract. Notice/horizon/conflict/cancellation rules are configurable; reschedule cutoff compares the old/new scheduled-time distance, not simply time remaining before start. Start/join permits the backend's 15-minute early window. Flutter submits actual note/reason/date fields and does not invent a scheduled end endpoint. Signaling validates input and updates lastSignalAt; it is not an SDP/ICE relay (B9).

Join returns provider/room/server URL/participant identity/access token/expiry/capability data. Flutter decodes credentials but has no LiveKit/WebRTC dependency, microphone/camera track code or media permission workflow. It explicitly shows unavailable media. ACCEPTED/STARTED is not evidence of a connected media session. This is a real incomplete functional requirement (F4), not a cosmetic limitation.

`video/service/LiveKitVideoMediaService.java:132–144` repeats/truncates the configured secret into 32 bytes before signing. That transformation is confirmed source behavior; compatibility with the actual LiveKit server is unverified and may fail for non-32-byte secrets. The existing token test checks token presence/metadata, not LiveKit acceptance. Room auto-provisioning also requires a real compatible server/client configuration. Do not promise the Flutter SDK alone will fix backend token compatibility. A webhook-signature helper without a mapped webhook controller is not completed webhook integration.

### Boosts, payments, invoices and support

Inspected boost plan/purchase/monitoring/analytics/invoice/checkout controllers and corresponding services, lifecycle jobs, invoice storage; support DTO/controller/service ownership. Purchase requires a verified lawyer and can conflict with an existing pending purchase for the same plan. Boost states include PENDING_PAYMENT, SCHEDULED, ACTIVE, EXPIRED, CANCELLED, SUSPENDED; payment states include INITIATED, PENDING, COMPLETED, FAILED, CANCELLED. Flutter uses returned status, paginates history/activity/invoices and refreshes after browser return.

Checkout returns a backend-provided public sandbox demonstration URL, with no Attorlink payment callback or user completion/cancellation route (B3). Internal activation/invoice code is not a user-accessible payment completion API. Production payment processing cannot be completed in Flutter against this unchanged contract. Invoices require owned records, generated/stored PDFs and authenticated download; Flutter checks PDF bytes and exports via the platform bridge. Per-boost daily analytics lacks a server ownership check (B2); the Flutter owned-detail precheck protects this app's workflow but cannot secure the API for other clients.

Sponsored profile visits need boostId + lawyerUserId + postId. Discovery and feed do not supply reliable boost linkage; `sponsored` is insufficient. Invalid linkage may produce a no-op rather than a meaningful visit, so a 200 alone would not prove tracking. This is M/B1, not a request to guess IDs. Support implements actual create/own paged list/owned detail/status refresh. There are no user ticket replies, priorities, status mutations, edits or deletes to add.
