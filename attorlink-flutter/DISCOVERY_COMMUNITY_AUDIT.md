# Phase 10C — discovery and community stabilization

2026-11-05. Current backend controllers, DTOs, relevant services/repositories, enums and security mappings were inspected read-only. This is **source, fixture and widget-test evidence**, not live backend or Android runtime proof. Backend/admin-panel contents, authentication source, dependencies, SDK source and system configuration were unchanged. The Phase 10B request-guard/session-generation infrastructure is reused.

## Actual contracts examined

All REST paths have prefix `/api/v1`. JSON endpoints retain the existing response envelope; page data contains `content,page,size,totalElements,totalPages`.

| Backend contract | Verified semantics |
| --- | --- |
| GET `/lawyers/discover`; GET `/practice-areas` | Public requests without bearer tokens. Discovery accepts `search,practiceAreaId,page,size`, trims/escapes the search, requires positive filter IDs and size, clamps size to 50, and sorts updatedAt DESC then id DESC. Only ACTIVE, VERIFIED LAWYER profiles qualify. Reference data is an ordinary active-item array. No client-selected sort or full other-lawyer profile endpoint exists. |
| Discovery response | `id` is the lawyer profile ID; `userId` identifies the account. Only fullName, profilePhoto, professionalTitle, bio, yearsOfExperience, practiceAreas and updatedAt accompany these IDs. Summaries display only these fields. Following APIs require **userId**, not profile ID. |
| GET `/community/feed` | Authenticated active CLIENT/LAWYER; modes FOR_YOU, FOLLOWING, LATEST, TRENDING, with page/size and a 50-item maximum. FOLLOWING is CLIENT-only. Feed queries apply author eligibility and server ranking; Flutter does not resort ranked pages. |
| GET/POST `/community/posts`; GET/PATCH/DELETE `/community/posts/{id}` | Lists and details, create, own update and soft delete. Create DTO: `type,text,mediaPublicId`; PATCH: `text,mediaPublicId`. Only TEXT/IMAGE creation is supported, maximum 5000 UTF-16 text units; TEXT requires nonblank text, IMAGE requires owned uploaded media. Active clients/lawyers may create; verified-lawyer eligibility is a feed-visibility rule, not a creation requirement. |
| POST `/community/posts/media` | Authenticated multipart `file` → `url,publicId,resourceType:image`. Media is owned by its uploader. Backend storage accepts JPEG/PNG/WebP up to 5 MB. Uploading does not create a post; replacement retains the old attachment unless a new public ID is supplied. |
| Post DTO and engagement | Post fields are id, authorId, type, textContent, deleted, timestamps, media URL/public ID, likeCount, currentUserLiked and sponsored. PUT `/{id}/like` **toggles**; DELETE removes a like. PUT/DELETE `/{id}/bookmark` explicitly save/remove. GET `/community/bookmarks` is paginated. POST `/{id}/share` creates a share receipt with id/postId/createdAt. No bookmarked flag, author name/avatar, comment/share totals or boost linkage is returned. |
| Comments and replies | GET/POST `/community/posts/{postId}/comments`; GET/POST `/community/posts/{postId}/comments/{parentId}/replies`. Page/size, createdAt ascending. The post-wide list includes replies; it is not a roots-only endpoint. POST/PATCH text is nonblank, at most 5000, and trimmed by the service. PATCH/DELETE `/community/comments/{id}` require ownership. Parent/post relationships, deletion and the post author's comment privacy are server-enforced. |
| Comment voting | PUT `/community/comments/{id}/vote` with `voteType:UPVOTE/DOWNVOTE`; selecting the existing vote toggles it off. DELETE explicitly removes it. Responses supply parentCommentId, authorId, text, deleted, timestamps, upvoteCount/downvoteCount/currentUserVote. No reply count is supplied. |
| Following | PUT/DELETE `/community/lawyers/{lawyerUserId}/follow`; GET `/community/following`; GET `/community/lawyers/{lawyerUserId}/followers`. Pagination uses page/size. Only ACTIVE CLIENTs follow ACTIVE VERIFIED LAWYERs; lists contain IDs/timestamps, not names. Unfollow returns a message-only envelope despite the service's internal DTO. |
| Reporting | POST `/community/reports` with targetType/targetId/reason/optional explanation (≤1000). Targets POST/COMMENT only. Reasons SPAM, HARASSMENT, INAPPROPRIATE_CONTENT, MISINFORMATION, OTHER. Own/deleted content and duplicate reason reports are rejected; actual receipt status is shown. No user-report or user-facing report-history/update route exists. |
| Analytics | POST `/community/feed-events` uses actual event enums and optional feedMode. GET `/community/feed-analytics?postId&from&to` returns impressions/clicks/likes/comments/shares/bookmarks/engagementRate/windowStart/windowEnd. LocalDateTime has no timezone, with fractional seconds preserved. The service requires a nondeleted post but currently aggregates **community-wide** events within the window; the UI describes that limitation. |

Post/comment/follow/report ownership, privacy, duplicate handling, exact HTTP methods and decoding were compared with the existing clients. No fabricated endpoint, status, successful response or user-profile data was added.

## Confirmed Flutter defects corrected

1. **Requests could cross authentication sessions while awaiting refresh.** Every community request now uses the Phase 10B access guard before dispatch/after token work and before response decoding. Repositories bind to the originating session generation and are disposed with their workspace. Logout/relogin to the same account cannot authorize old requests. Saved post/comment responses also validate author and thread identity.
2. **Cached views missed changes from other entry points.** Confirmed or uncertain mutations now invalidate shared community views. Visible feeds reconcile through REST; offstage/covered feeds defer until visible. This also covers mutations through the existing notification routes, which borrow the same repository. Post reads returning 404/403 invalidate cached views; inaccessible post/comment operations remove stale detail/thread rows. Tracking events do not invalidate feeds or create reload loops.
3. **Session replacement could briefly display old personalized rows.** Replacing a feed's repository clears its old rows/category/errors immediately, before the new request completes. Late feed/tracking responses are generation-bound. Listeners are removed during disposal.
4. **Overlapping pages discarded edits and tombstones.** Discovery, feed and comment/connection pagination merge by stable identity, replace previously loaded fields with the latest returned version, and remove returned deleted rows. Current ordering is retained until refresh; duplicate keys are avoided. Backend page numbers remain authoritative.
5. **Discovery lacked a usable link to existing following workflows.** Summaries can open the existing lawyer-connections screen with the actual userId. Backend eligibility remains authoritative. Confirmed own-lawyer profile changes invalidate discovery results while preserving the active search/filter; ordinary navigation still preserves search state.
6. **Rapid callbacks could duplicate operations.** Post create/upload handlers now guard busy/uncertain/saved state inside the handler. Detail reloads coalesce; delete/share confirmations cannot stack, and deletion captures its target before waiting. Existing comment/report/follow mutation guards remain intact.
7. **An unknown upload outcome could be replayed.** An ambiguous media-upload response blocks another upload in that draft. Previously confirmed media remains available; text-only saving remains possible. Picker failures before transfer do not cause this lock. No unattached-upload lookup/cleanup endpoint is invented. Backend field-level validation feedback is now retained across community forms.

## Backend limitations and unresolved risks

- **Visibility is inconsistent across backend APIs:** feed queries filter active authors/verified lawyers; general post list/detail services currently check only deleted=false. Responses omit author status/verification, so Flutter cannot implement an equivalent visibility check. Backend-owner review and real authorization tests are required; the original backend was not modified.
- There is no dedicated own-post endpoint, so My posts filters the general visible-page collection and its totals are not own-post totals. There are no general other-lawyer details, user reports, unsupported post-type creation, bookmark-state field, media-removal PATCH, unattached community-upload inventory, or stable cursor/snapshot API.
- Offset/ranked pagination can shift between requests. Identity merging fixes returned overlaps and tombstones, but cannot recover records that the server skips or deletions it never returns. Explicit refresh remains necessary for unrelated external changes; realtime community updates are not invented.
- An upload whose response is lost may leave an unreachable stored object. Previously confirmed upload IDs are retained for save retries, but unknown IDs cannot be safely recovered or deleted. Storage/post saves are not atomic; standalone asset cleanup remains a separate gap.
- Unfollow and follower-list services require the target lawyer still to be active/verified. Removing a follow to a lawyer who has lost eligibility may therefore fail server-side. Flutter surfaces the actual error and does not pretend removal succeeded.
- No additional confirmed Flutter defect remains unresolved in the reviewed scope. Android adapters, real API authorization, response timing and storage behavior remain unverified; passing fixtures do not establish production readiness.

## Runtime prerequisites and recommended next phase

A confirmed disposable Spring Boot environment with MySQL, Redis, appropriate CLIENT/LAWYER accounts, verified discoverable lawyers and active reference data is needed for end-to-end verification. SMTP is required for genuine authentication setup, and Cloudinary plus network access is required for real image upload/retrieval/deletion. Android network configuration, native picking, secure sessions and process restart remain separate device-checkpoint work. Flutter must access external services through Spring Boot.

Recommended next source phase: **messaging, notification and realtime synchronization stabilization**, including session lifecycle, REST cursors, tombstones and reconnect reconciliation. Keep Android/native and full-stack runtime verification in their approved checkpoints. Do not continue automatically from Phase 10C.
