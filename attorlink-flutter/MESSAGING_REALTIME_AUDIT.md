# Phase 10D — messaging, notifications and realtime stabilization

2026-11-05. Inspected current chat/notification controllers, DTOs, services, repositories, WebSocket configuration, publication paths and relevant security mappings read-only. Phase 10A–10C corrections are retained. Results are **source, fixture and widget-test evidence**, not live backend, SockJS or Android runtime proof.

## Backend contracts examined

REST prefix: `/api/v1`. Existing response envelopes and page metadata are retained. The frontend requests 20-item pages; chat controllers cap page size at 50 and notifications at 100.

| Contract | Actual behavior |
| --- | --- |
| POST `/chat/conversations` | `recipientUserId`, optional `firstMessageText` (≤4000). Active CLIENT/LAWYER participants; CLIENT_LAWYER or LAWYER_LAWYER pairs, no client–client chat. Recipient privacy can require following. Returns an existing conversation or creates PENDING, persisting optional initial text only for a new pair. No fabricated recipient identity/profile lookup or reopen action. |
| GET `/chat/conversations`, `/{id}`; GET `/chat/requests/incoming`, `/outgoing` | Participant-bound DTO: IDs, conversationType, initiatedByUserId, requestStatus, timestamps and unreadCount. Lists sort updatedAt DESC/id DESC. Incoming is recipient-PENDING; outgoing has a backend pagination defect described below. |
| POST `/chat/conversations/{id}/accept`, `/reject` | Intended recipient only, PENDING only. Confirmed status must be ACCEPTED or REJECTED respectively. Permissions are server-authoritative. |
| GET/POST `/chat/conversations/{id}/messages` | Oldest-first history, createdAt ASC/id ASC. History can be read while pending; ordinary text send requires ACCEPTED. POST `{text}` is nonblank, ≤4000, normalized by the server. Stable server IDs are preserved; there is no client idempotency key or attachment-send API. |
| PATCH/DELETE `/chat/conversations/{id}/messages/{messageId}` | Own eligible messages in accepted conversations. PATCH `{text}` edits TEXT only; DELETE returns a ChatMessageResponse with isDeleted/deletedAt, potentially retaining text in its raw DTO. Flutter discards deleted text and keeps the deletion marker. |
| POST message `/{messageId}/delivered`, `/seen`; POST conversation `/read` | Recipient acknowledgement, not a locally inferred receipt. Read body is `{lastReadMessageId}`; response contains conversationId, lastReadMessageId and markedSeenCount. Marking delivered preserves an existing SEEN state. Receipt rows are per user; pending history acknowledgement is not blocked by an invented accepted-only restriction. |
| GET conversation `/sync` | `lastMessageId`, `lastEventTimestamp`, `limit` (1–200). Real existing message cursor required. Returns messages, tombstones, hasMore, nextCursorMessageId/nextCursorCreatedAt. Cursor compares event timestamp then ID; deletion events can advance to an older message ID. Exact timezone-free timestamp strings/nanoseconds are retained. The query tracks creations/deletions, not edit/receipt updates. |
| GET `/notifications`, `/unread-count`; PATCH `/{id}/read`, `/read-all` | Own notifications only; createdAt DESC/id DESC. Read-one returns NotificationResponse; count fields are `unreadCount` and `updatedCount`. DTO supplies recipientId, actorId, type, title/message, relatedEntityType/Id, eventId, read and timestamps. No user-facing delete, unread-reset or device-push registration API was found in these controllers. |

Some chat services use **HTTP 400 for access/status denials** as well as validation. This cannot be handled solely by treating 401/403 as authorization failures. Metadata/history requests have no editable form fields: a rejected access check now fails closed; actual mutation validation preserves the draft and revalidates conversation access when needed.

### SockJS/STOMP contracts

- `WebSocketConfig` registers a SockJS endpoint from configuration. The checked `application.yml` defaults `WEBSOCKET_ENDPOINT_PATH` to **`/ws`**, overriding the AppProperties fallback `/ws/chat`. Flutter's `ATTORLINK_SOCKET_PATH` must match deployment/proxy configuration. No backend configuration was edited.
- SDK transport performs GET `/ws/info`, then `ws(s)://host/ws/{serverId}/{sessionId}/websocket`. SockJS `o/h/a/c` framing and STOMP 1.2 framing are used. This is **SockJS WebSocket transport only**, with no XHR/streaming/polling fallback.
- JWT appears only in the STOMP CONNECT native `Authorization: Bearer …` header. Backend rejects a query-string JWT. CONNECT checks the actual user and ACTIVE status; allowed origins remain backend-controlled. No origin, CSRF, authentication or TLS restriction is bypassed.
- Supported subscriptions are `/user/queue/notifications` and `/user/queue/chat/conversation/{id}`. Conversation subscriptions require authenticated participation and ACCEPTED status. No public-topic subscription is used.
- NotificationDeliveryService publishes plain NotificationResponse after commit. The reviewed ChatWebSocketController handles `/app/chat.send` and publishes plain ChatMessageResponse to both participants' private conversation queues. The security configuration also whitelists an alternate send pattern, but no corresponding handler was found in this controller; Flutter does not invent one.
- Flutter sends through REST and does not automatically resend a message through STOMP. REST send/edit/delete/receipt services do not themselves publish conversation message updates through that controller. Periodic/on-reconnect REST synchronization and bounded rotating history reads remain necessary. STOMP subscription ack=auto is not treated as a business delivered/seen acknowledgement.

## Flutter defects corrected

1. **Cross-session REST dispatch and queued events:** chat/notification repositories now bind to the authentication generation and use the existing request access guard around async token work, dispatch and decoding. Workspace/bootstrap wiring supplies that generation. Consumers reject queued old-generation LiveEvents even after relogin to the same user ID. Send/change/decision/ack responses validate the relevant author, status and identity rather than assuming success.
2. **Old pending work blocked new sessions/resume:** credential/count flights are independently owned and invalidated on identity/lifecycle changes. Their late results or failures cannot overwrite or tear down a replacement session. Count invalidation suppresses an earlier unread response until the replacement read completes; an older inbox count cannot overwrite a later confirmed count event.
3. **Content and receipt reconciliation conflicted:** timeline merge now chooses content by version and confirmed receipt monotonically, independently. An older-body SEEN response cannot erase an edit or lose its receipt; a newer-body SENT response cannot undo SEEN. Tombstone timestamps do not regress, deleted text cannot reappear, and history cannot reseed an established event cursor.
4. **Refresh/load races:** history refresh preserves newer known versions instead of clearing them, metadata applies only to its request revision, refreshes coalesce, and live inbox refresh/load-more cannot overwrite one another. Overlapping inbox pages adopt updated records. Message events arriving before initial thread metadata now queue REST reconciliation instead of being dropped until the next periodic tick.
5. **Access denial retained private content:** metadata/history denial, including the backend's 400 contract, clears cached messages/cursors and releases affected subscriptions. Mutation form errors retain drafts. The thread no longer presents the detail endpoint's default unreadCount=0 as an authoritative unread total; inbox totals still use the list service's computed values.
6. **Lifecycle/transport cleanup:** initially suspended applications defer activity; non-resumed lifecycle states pause sockets and periodic polling. Resume reconciles through REST. Chat reconciliation checks suspension between reads; already-dispatched work may complete. Native close has a bounded wait and always closes its HttpClient. Unsupported SockJS WebSocket capability stays in REST mode until explicit reconnect/new session, instead of retrying every poll. Existing backoff and reference-counted subscriptions are retained.
7. **Notification/read and interaction races:** confirmed read-all updates only the captured notifications, preserving later arrivals as unread without fabricating readAt. Ambiguous read outcomes reconcile through GETs. Event processing uses a bounded throttle instead of continually postponing under a busy stream. Request decisions/edit/delete confirmations cannot stack; uncertain sends retain their drafts and require explicit review before a new send.

## Backend limitations and unresolved risks

- **No exactly-once send guarantee:** the API has no client message key or deduplication lookup. An unknown POST result cannot be safely replayed automatically. User review reduces accidental duplication but cannot prove whether an indistinguishable prior send committed.
- **Incomplete event stream:** REST edits/receipts are absent from incremental sync and chat broadcasts. History reconciliation is required; offline periods, shifted offset pages, network failures and missed unsubscribed conversation events can delay convergence. An empty conversation has no fabricated zero/epoch cursor; history must discover the first actual message. Loaded-page reconciliation costs and recovery under large backlogs still need runtime measurement.
- **Outgoing-request pagination:** the service filters each general inbox page and constructs totals from that filtered subset. Later requests may be hidden by incorrect hasMore metadata. Existing Sent conversations/status filtering across the normal inbox is the available alternative; the original backend was not changed.
- **Counts/receipts are not universal:** GET conversation detail uses the DTO overload defaulting unreadCount to zero, while inbox lists calculate it. Delivery rows/history status are computed for the current viewer, so the sender may still receive SENT after the recipient acknowledged SEEN. Flutter shows confirmed values and does not infer the other participant's read status. Backend-owner review and two-user testing are required.
- **In-app only:** there is no mobile push implementation here. Background socket/polling pauses; resumed/foreground views reconcile through REST. Already dispatched HTTP work cannot be canceled through the existing transport interface. Android process death, OS background policy, TLS/origin/CSRF deployment behavior and real reconnection/resource cleanup require device/backend evidence.
- Notification CHAT_MESSAGE IDs are not conversation IDs; VIDEO_CALL IDs do not identify immediate vs scheduled namespace. Existing navigation opens the supported inbox in these cases. Post/conversation destinations retain their guarded 404/permission handling; unavailable targets are not represented as successful navigation or successful reads.
- No additional confirmed, fixable Flutter defect remains open in the inspected scope. Live delivery, actual server authorization, cross-device ordering and full native lifecycle behavior remain **unverified**; fixture passes are not production-readiness proof.
