# Phase 10E — remaining features source audit

Date: 2026-11-05. Backend inspection was read-only; admin-panel untouched. This is source/fixture validation, **not live integration or Android runtime proof**. Phase 10A–10D corrections are retained.

## Contracts examined

## Confirmed Flutter corrections

- Calls, boosts, settings and support now pass session access guards through every REST request, including PDF download. Guards run after awaited token work/recovery and before response decoding. Settings/support capture authentication generation, and support opened from Settings retains its parent's session binding. Same-user relogin also invalidates old repositories. Late security responses cannot sign out or recheck a replacement session.
- Call action/reschedule confirmations and security/destructive confirmations serialize interactions. Call polling pauses during confirmations/rescheduling and app suspension; call events reject old authentication generations. State/permission failures lock further lifecycle actions until an authoritative read; inaccessible call/list, support detail/list and boost detail data is cleared. No call signal or uncertain mutation is automatically replayed.
- Call credentials must match the actual provider/current-user media identity, call namespace and room. Immediate-call forms no longer offer a note the backend discards. No UI reports actual audio/video connection from ACCEPTED/STARTED.
- Purchase pages merge by backend ID, updating overlapping rows. Failed boost detail/checkout operations retire old handoffs; inaccessible detail responses clear stale purchase data. The existing verified-profile check, conflict/uncertainty lock and backend-authoritative payment state are retained.
- Per-boost daily analytics now first calls the backend's owned-detail endpoint. This protects the Flutter workflow; it **does not repair the unguarded backend daily endpoint** against independent clients.
- Added SDK-only Android HTTPS ACTION_VIEW checkout opening and ACTION_CREATE_DOCUMENT PDF export. A separate destination-selection step precedes the PDF write; session access is rechecked before sending bytes after picker completion. Native code validates PDF signature and chosen destination, serializes export, writes off the UI thread and cleans up channel results on activity destruction. No broad storage permission, third-party package or silent payment confirmation. Dart channel tests passed; native code remains uncompiled/unexercised in this phase.
- TOTP/password/OTP fields clear whenever the security flow leaves resumed state; late setup responses cannot re-expose cleared enrollment secrets. Shared error rendering now includes backend field validation errors. Android export/checkout responses recheck access before showing completion notices.

## Incomplete functionality and backend limitations

- **Actual audio/video media remains an incomplete functional requirement.** There is no Flutter LiveKit/WebRTC transport, camera/microphone session, OS incoming-call service or background push. Credential issuance/lifecycle APIs are implemented but cannot establish a media session. Backend LiveKit server, API credentials, provisioning and token compatibility must be genuinely tested; these were not exercised.
- **Production payments remain incomplete.** The sandbox demo handoff is not an Attorlink payment callback. Opening it cannot complete payment or activate a boost. No reviewed client endpoint allows payment completion or cancellation; production provider/callback work needs separately authorized backend-owner work, not Flutter fabrication.
- Backend ownership gap: `BoostAnalyticsServiceImpl.getBoostDailyMetrics` checks existence but does not call the ownership check used by summary/detail. Controller role authorization alone does not protect another lawyer's analytics. Backend owner remediation/review is required before production; original backend remains unchanged.
- Call creation, scheduling, ticket creation and purchase initiation have no client idempotency key. Busy/uncertainty guards prevent blind replay within these screens; they cannot guarantee exactly-once execution across retries, app restarts, multiple screens/devices or lost responses. Review authoritative history before another attempt.
- LocalDateTime lacks a server timezone contract/config discovery API. Device/server zone disagreement cannot be resolved by inventing UTC conversion. Backend reschedule/cancellation rules, lack of scheduled-call end action and non-relayed signaling remain authoritative limitations.
- Offset pages can shift under concurrent writes. Purchase IDs allow deduplication, but missing records still require refresh; daily analytics lack stable per-row identity and cannot be safely deduplicated across account pages. Support has no consistent snapshot cursor.
- Session DTOs lack current-device/IP metadata, security history is unpaginated, and refresh revocation does not prove immediate invalidation of issued JWTs. There is no dedicated 2FA recovery-code API or deletion-status endpoint. Re-running TOTP setup replaces the saved enrollment secret. Unknown security outcomes require status review rather than automatic retries.

## Remaining source risks and later runtime checks

No additional confirmed fixable Dart defect remains open in the inspected scope. This is not a completeness or production-readiness claim. New Android bridge Kotlin has not been compiled, and picker/browser/provider behavior, activity/process recreation and OS lifecycle need actual evidence. A write already dispatched to a document provider cannot be revoked by subsequent logout; interrupted exports may leave partial/empty documents. Existing desktop invoice saving checks for an existing path but does not guarantee atomic no-clobber against another filesystem writer. iOS/Windows platform limitations remain as previously documented. Web export was analyzed, not compiled or browser-tested here.

Later tests require a confirmed disposable Spring Boot/MySQL/Redis environment, genuine active CLIENT/LAWYER accounts (verified lawyers for call/boost eligibility), SMTP for OTP/security/support email, configured storage for invoice PDFs and provider uploads, and a real LiveKit environment for media. Never connect Flutter directly to these services.

Recommended next phase: an explicitly scheduled **Android adapter/native compilation checkpoint**, followed by device lifecycle/session/picker/browser/export tests and a disposable two-account end-to-end matrix. Test conflicting call transitions, scheduling windows/server zone, lost responses, account switching while requests/pickers are pending, checkout return without payment, backend-confirmed payment/invoice states, wrong-password/expired OTP/2FA/session revocation/deletion grace, and owned support pagination. Obtain approval before any missing dependency installation or infrastructure startup. Do not resume media/payment implementation or runtime testing automatically.
